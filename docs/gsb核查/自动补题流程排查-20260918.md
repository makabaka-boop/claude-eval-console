## 必须保留的规范要求

- 使用 auto、相同环境及原文题面，A/B 各一个独立首轮；不追加交互。
- 简单、中等题禁止；从人类执行视角如实判断难度。
- 避开禁题和实质雷同，保留真实轨迹、共同初始快照、独立产物快照与录屏。

“1:1:1 配比目标”“45 分钟实现加 15 分钟验证”“首次 Feature 必须完整新模块”“300–480 字、4–6 句”“特殊机制数量上限”等属于本地策略，不能说成 GSB 原规范的直接要求。原规范继承的是三类题型优先于其他类型的分布偏序；Feature 的定义是已有功能上的平滑扩展。保留本地质量偏好可以，但应统一口径，并避免阻塞所有可执行类型。

## 1. 确定的实现错误：首次出题也被告知已遭规则 C 拒绝

位置：`pairwise/auto_refill.py:781–786`，`app.py:5386–5392`、`app.py:5419–5422`。

自动生成无条件将“只读检查临时 main……”加入 feedback，随后因 feedback 非空而写入 `_concept_retry_feedback`。概念生成器把该字段的任何非空内容解释成规则 C 拒绝：Feature 要求“彻底放弃其业务对象、操作原型和页面位置”，Bug 要求改查不同缺陷家族。

因此即使没有上一次候选、没有真实查重结论，首次出题也会得到虚假的拒绝历史。普通错题本提示和难度意见也被混在这个字段内。Bug 同时还被要求只能检查已经固定的 seeded/existing defect，进一步产生“只查这一条，但又要换缺陷家族”的冲突。

验证：拦截 `run_codex_structured`，只传普通只读提示，在 Bug、Feature 两种最终提示词中均复现虚假的规则 C 拒绝句；未调用模型。

修正方向：通用执行要求、错题本资料、难度反馈、经确认的重复证据分别传递；仅在确有规则 C 结论时使用换方向指令。

## 2. 调度缺少“长期没有产出”的跨题型兜底

位置：`pairwise/auto_refill.py:365–373`、`pairwise/auto_refill.py:528–557`、`pairwise/auto_refill.py:1553–1576`，`pairwise/sources.py:188–207`。

主通道按数量选最少类型，4:3:0 会持续优先 Bug。备题通道给正在生成的 Bug 加 4，得到 4:3:4，又优先 Feature。只要还有能通过来源资格的 Bug/Feature 基线，这两条通道就不会因“已经很久没有产出”主动转去新 0-1。

当前按题型暂缓的条件仅覆盖至少三个仍在冷却、且原因含超时的不同来源。难度不足、规则 C、预置前后对照失败等不会直接触发同等的题型级兜底。来源冷却 30 分钟后又能进入候选，来源可用不等于当前能从它生成合格题。

验证：使用现场计数运行纯调度选择，主通道选 Bug，备题选 Feature；与实时状态一致。这是进展饥饿问题，不是互斥锁死锁。

修正方向：保留题型配比目标，同时根据连续无产出次数或累计生成预算暂缓该类型；当 Claude 空闲、库存为零且迭代题持续失败时，为新的 0-1 留出生成机会。

## 3. Bug 当前反复失败于预置缺陷的对照验证，错误证据又被丢弃

位置：`pairwise/seeded_bug.py:99–114`、`pairwise/seeded_bug.py:171–202`；`pairwise/auto_refill.py:865–907`。

最近多条失败记录是“预置前后未证明同一用户场景由通过变为失败”，并伴随 seeded-bug-patch 超时。22:52 还有一条已复现的预置故障被判为常规矩阵比较即可修复，只达到中等。这说明“补丁造成故障”与“最小必要修复达到困难”是两个独立条件，不能互相替代。

代码将原始快照和预置快照分别克隆后直接执行 regression_command，仅检查 before.returncode 和 after.returncode。前者非零、后者仍为零都会抛同一句错误；返回码、stdout、stderr 没有随这条异常保存。原有固定验收在另一个临时副本运行，两个对照副本不继承其依赖或启动状态，复现命令必须自行准备运行环境。

目前保存的历史不足以区分“原快照环境没准备好”“命令断言不正确”“补丁根本没触发”等根因，不能直接认定所有这些记录都是业务缺陷设计失败。

修正方向：保存对照命令、两侧退出码和输出，区分环境失败与行为断言失败；先建立可运行的基线复现，再验证补丁使同一行为失败。独立困难审核仍然保留，不能为增加产出放行中等修复。

## 4. Feature 的可选增量被本地规则过度收窄

位置：`pairwise/auto_refill.py:787–793`，`app.py:5370–5384`、`app.py:6594–6599`。

首次 Feature 被固定为完整新模块，要求新对象、新生命周期和新主流程。最终审核提示词仍保留：两种 Feature 形态都不能把历史主结果继续做应用、确认、导出、配置、局部、批量或更细粒度版本。

这比“禁止重复已验收的相同需求”更宽：某些真正新增、具有独立结果的平滑扩展，在比较具体行为之前就被禁止。它也把完整模块建设和 Feature 平滑扩展混成了同一个必选路径。

现场表现：23:26 的录音暂停/恢复、23:35 的字幕权重参数化，被独立复核判为中等；22:52、22:58 的跨标签页发布协调又被判范围超大。这些具体难度拒绝有实际代码依据，不能一概视作误判。问题是候选空间过窄，导致反复在“小增量不够难”和“完整模块超预算”之间切换。

修正方向：允许基于已有对象的真实困难增量；查重以核心行为和用户验收结果是否已经完成为准，不能仅因属于确认、批量等操作类别就禁止。完整模块可作为一种候选形态，而非所有首次 Feature 的强制前提。

## 5. 0-1 生成口径与硬校验不一致，文字偏好也在消耗候选

位置：`pairwise/auto_refill.py:16–23`，`app.py:4086–4088`、`app.py:4413–4428`、`app.py:5923–5949`、`app.py:6740–6741`。

ROOT_DEPTH_GUIDANCE 要求至少两个可分别操作和验收的功能模块，并允许多个必要技术难点；下游仍限制复杂机制与自定义算法合计最多一项。两个关联功能不必然违反一项机制预算，但这两套表述没有解释边界，生成器可能按前者扩展、随后被后者拒绝。已在最终发给模型的同一提示词中确认两套要求同时存在。

Feature 仍把 300–480 字、4–6 句等作为硬校验，本地错题本有 481 字、482 字被拒绝的实际记录。审核还规定表达像结尾验收清单时，即使技术内容完整也必须 approved=false；程序对非空 ai_style_issues 继续硬拦截。

修正方向：统一范围规则的唯一来源；把可独立修复的文字格式问题送到保留需求的定向改写，不应消耗一次业务方向或来源失败。真正的题意歧义、实质重复、过大范围和难度不足继续硬拦截。
