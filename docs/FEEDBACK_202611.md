## 核心流程变化

| 项目 | 旧版 GSB 流程 | 11 月专项要求 |
| --- | --- | --- |
| 数据单位 | 同题 A/B 两次执行组成一条数据 | 一个 Session 的一轮有效交互组成一条数据 |
| 模型执行 | 两个独立会话进行比较 | 使用 auto，只跑首轮，回答结束后不追问、不纠错 |

| 提交组织 | 现有 GSB 导出与提交流程 | 按专项模板维护正式提交表，具体模板和接入方式待确认 |

## 任务类型

附录定义了 11 个一级标签：

1. 功能开发：包括 0-1 开发和 1-n 开发。
2. Bugfix。
3. 代码重构。
4. 功能优化。
5. 依赖升级与迁移。
6. 质量保障。
7. 项目维护。
8. 技术讨论。
9. 问题排查与诊断。
10. 部署运维。
11. 泛 Agent 需求。

旧版“0-1 代码生成”和“Feature 迭代”在新的一级标签中归入“功能开发”。具体边界以 PDF 第 11–12 页的涵盖场景和口径说明为准。

## 提交字段

| 字段组 | 字段 |
| --- | --- |
| 题目与环境 | User Prompt、所属领域、子方向、任务类型、任务难度、语言/框架、Harness、Harness 版本、操作系统、环境可复现等级、初始环境快照 |
| 会话与产物 | SessionID、TurnID/PromptID、轨迹文件、产物快照、运行录屏 |
| Feedback 评价 | 交付完整性、Feedback |
| 其他 | 备注；多模态题另需 prompt 附件 |

环境可复现等级为选填；交付完整性和 Feedback 为必填。User Prompt 保留完整原文。Codex CLI 的 TurnID 取 `task_started` 事件的 `turn_id`，Claude Code 的 PromptID 取本轮 user 消息的 `promptId`。依据：PDF 第 2–3、10 页。

## 执行与证据要求

- 难度仅允许“困难”和“地狱”，按人类专家执行视角判断。
- 全程使用 auto，最大上下文保持 1,000,000，不在作业期间修改配置。
- 开始前保存并推送初始工作区快照，记录 40 位完整 SHA 的 commit permalink。
- 结束后保存并推送产物快照。模型已有多个提交时填最后一个，保留提交历史；初始快照必须是其祖先。
- 保存原始轨迹 JSONL、SessionID 和 TurnID/PromptID，并提供可直接下载的轨迹链接。
- 从干净状态录制产物的真实运行，视频不超过 90 秒；无法运行时也录制报错过程，不剪掉失败片段。
- 提交后的快照保持可达，不通过 force-push 或 rebase 改写已提交历史。凭据、密钥和真实连接串不得进入仓库。

依据：PDF 第 2–6 页。正文与后文存档表述的冲突列在“待确认事项”。

## 人工 Feedback 要求

文档明确禁止使用 AI 工具分析轨迹、产物或代写 Feedback。专家人工核对过程和产物后填写评分与反馈；系统的采集、归档、上传和字段校验与人工标注分开设计。

Feedback 同时说明执行过程和最终产物，定位到触发节点、实际行为和业务影响，给出具体文件、报错或缺失需求。交付完整性为 4–5 分时，也要写出核对过的需求点、实际运行验证结果和过程表现。网络故障、部署导致的推理时长等因素不作为模型能力问题扣分。

依据：PDF 第 1、3、7、12–15 页。

## 交付周期

- 周期：2026 年 11 月 10 日至 12 月 15 日，产出不少于 15,000 条数据。
- 团队日产量：除爬坡或模型无法提供服务等情况外，每天 500–1,500 条。
- 当天 20:00 前产生的数据当天提交，20:00 后产生的数据允许次日提交。
- 不允许返修，不合格数据直接拒收。

依据：PDF 第 1 页。
