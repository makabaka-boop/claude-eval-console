## 核心流程变化

| 项目 | 旧版 GSB 流程 | 11 月专项要求 |
| --- | --- | --- |
| 数据单位 | 同题 A/B 两次执行组成一条数据 | 一个 Session 的一轮有效交互组成一条数据 |
| 模型执行 | 两个独立会话进行比较 | 使用甲方模型和 Key 执行单轮任务；自行中断允许“继续”，不追加新需求或纠错题面 |
| 评价字段 | 两侧交付完整性评价与 GSB 比较 | 交付完整性 1–5 分整数和一段整体 Feedback |
| 出题分类 | 原来的工程任务分类 | 每人本期固定一个领域，任务记录子方向及附录中的新任务类型 |
| 会话定位 | A/B 两组 SessionID | 提交首轮 SessionID 和 TurnID/PromptID；续写 ID 内部完整保留 |
| 产物历史 | 初始快照直接作为产物提交的父提交 | 初始快照是最终提交的祖先即可；保留中间提交，不 squash |
| 提交组织 | 现有 GSB 导出与提交流程 | 按专项模板维护正式提交表，具体模板和接入方式待确认 |

依据：PDF 第 1–3、5–7 页。

## 领域与子方向

| 所属领域 | 明确列出的子方向 |
| --- | --- |
| 安全 | 漏洞检测与攻防、身份认证、网络与通信安全、系统安全、其他 |
| 游戏、图形与多媒体 | 音视频处理、图形渲染、游戏开发、图像处理 |
| 数据工程 | 数据采集、爬虫与 RPA；数仓与数据湖；数据分析与数据应用 |

题目应来自对应领域的真实工程需求。正文允许跨子方向、涉及上下游链路或边界难以界定的真实任务使用“其他”兜底；正式模板中各领域的枚举项需核对。依据：PDF 第 4–5 页。

群公告要求每人只能选择一个领域。同一个 Repo 可以出多道独立题目，不再进行 A/B 或多轮对比。个人领域可在实际出题前最后选择，不影响通用模块改造；选定后在本期使用该领域。

## 提交字段

| 字段组 | 字段 |
| --- | --- |
| 题目与环境 | User Prompt、所属领域、子方向、任务类型、任务难度、语言/框架、Harness、Harness 版本、操作系统、环境可复现等级、初始环境快照 |
| 会话与产物 | SessionID、TurnID/PromptID、轨迹文件、产物快照、运行录屏 |
| Feedback 评价 | 交付完整性、Feedback |
| 其他 | 备注、群公告要求的“其他问题”；多模态题另需 prompt 附件 |

环境可复现等级为选填；交付完整性和 Feedback 为必填。User Prompt 保留完整原文。Codex CLI 的 TurnID 取 `task_started` 事件的 `turn_id`，Claude Code 的 PromptID 取本轮 user 消息的 `promptId`。中断续写时仍提交首轮定位，综合评价全部续写内容，在“其他问题”说明中断情况。依据：PDF 第 2–3、10 页和群公告。

## 执行与证据要求

- 难度仅允许“困难”和“地狱”，按人类专家执行视角判断。
- 执行继续使用甲方提供的模型及 Key；PDF 的 auto、1,000,000 上下文要求沿用，执行配置与评价分析配置分开。
- 模型自行中断时允许输入“继续”，保留同一 Session 内的所有续写，不增加新的提交样本；不能借“继续”追加新需求或纠错提示。
- 开始前保存并推送初始工作区快照，记录 40 位完整 SHA 的 commit permalink。
- 结束后保存并推送产物快照。模型已有多个提交时填最后一个，保留提交历史；初始快照必须是其祖先。
- 保存原始轨迹 JSONL、SessionID 和 TurnID/PromptID，并提供可直接下载的轨迹链接。
- 从干净状态录制产物的真实运行，视频不超过 90 秒；无法运行时也录制报错过程，不剪掉失败片段。
- 提交后的快照保持可达，不通过 force-push 或 rebase 改写已提交历史。凭据、密钥和真实连接串不得进入仓库。

依据：PDF 第 2–6 页。正文与后文存档表述的冲突列在“待确认事项”。

## 分析模型与 Feedback 要求

群公告明确要求分析轨迹、撰写评价描述使用 GPT 6.1 Sol 的 high 推理等级，禁止使用 DeepSeek。这条补充更新了 PDF 的禁止 AI 条款，后续按指定模型分析、保留依据并复核的方式实施。

分析模型计划配置为 `gpt-6.1-sol`，显式传入 `reasoning_effort=high`；实际服务的标识在接入时核对。保存请求模型、推理等级、分析范围和原始分析结果，避免旧版 `gpt-5.6-sol` 或 medium 默认值进入新专项分析。执行模型和甲方 Key 不因分析配置而被替换。

Feedback 同时说明执行过程和最终产物，定位到触发节点、实际行为和业务影响，给出具体文件、报错或缺失需求。发生中断时，分析覆盖原始执行及所有续写。交付完整性为 4–5 分时，也要写出核对过的需求点、实际运行验证结果和过程表现。网络故障、部署导致的推理时长等因素不作为模型能力问题扣分。

提到测试通过数量时，优先聚焦与本题需求相关的测试文件和场景，并保留原始输出依据；不强制为了写评价而统计测试数量，也不以整个仓库的测试总量代替本题验收。

依据：群公告第 3、4、7、8 条，以及 PDF 第 3、7、12–15 页中未被公告更新的证据要求。

## 交付周期

- 周期：2026 年 11 月 10 日至 12 月 15 日，产出不少于 15,000 条数据。
- 团队日产量：除爬坡或模型无法提供服务等情况外，每天 500–1,500 条。
- 当天 20:00 前产生的数据当天提交，20:00 后产生的数据允许次日提交。
- 不允许返修，不合格数据直接拒收。

依据：PDF 第 1 页。

## 后续系统改造范围

以下为基于本期需求的改造安排，尚未实现：

1. 增加单会话任务流程，支持同仓库多题；自行中断允许“继续”，全部续写归并到首轮样本，旧 A/B 数据作为历史归档保留。
2. 增加个人固定领域、任务子方向，更新任务类型及难度选项，保存首轮和续写定位、多模态附件及“其他问题”。
3. 建立独立的 `gpt-6.1-sol` high 分析链路，覆盖完整执行和全部续写，生成同时含结果与过程的 Feedback，再复核和确认交付完整性。
4. 更新产物归档，保留模型已有提交，以祖先关系核验初始快照与最终产物。
5. 按确认后的正式模板更新导出和提交映射；专项提交入口确认后再接入上传流程。
6. 将旧版题型配比、范围预算等内部工具配置与本期官方提交要求分开管理。

2. **专项方向与禁题列表交叉**：粒子、RBAC、业务报表等能力出现在专项方向中，对应的常见应用也出现在第 8–9 页禁题列表中。具体工程机制与雷同应用之间的边界需确认。
3. **提交模板与渠道**：第 2 页要求维护正式提交表，截图仍有 `A-User Prompt` 表头；完整字段、枚举及“其他问题”的映射需核对，不能据此推定旧 SOLO-QA GSB 接口适用。
