## Feature / Bug 直接题面生成（2026-09-23，当前 `generation-v50`）

- Feature 迭代和 Bug 修复的最终题面由 `gpt-5.6-sol / high` 直接在对应项目目录读取代码后生成。Feature 采用“完整模块构建、最好跨模块多文件、单段可转发、不设计多天验证或高并发需求”的自然指令；Bug 采用“多个问题、稍难、只总结问题不写解决方法、单段可转发”的自然指令。
- 最终题面生成只接收已批准概念卡或冻结故障、必要项目材料与结构化输出字段，不携带范围、难度、查重、真实性或文风政策，也不在生成 schema 中提前限定这些准入值。
- 所有验证规则保留：生成后仍依次执行确定性本地校验、同仓库/GSB 语义查重、Bug 真实性审核、Feature/Bug 范围和难度独立审核、文风检查及最终准入。
- 验证只指出题面表达、遗漏或范围可修正问题时，将意见交回同一模型改写同一概念或同一冻结故障并再次验证；不会借改写更换 Bug 或另起需求方向。
- Feature 概念筛选不变；Bug 的两路现有缺陷发现、独立复核、两路失败后埋 Bug、植入安全约束和冻结源码盲审均不变；0-1 流程不变。

## 0-1 出题范围收敛（2026-09-22，`generation-v40`）

- 0-1 以 45～60 分钟为设计目标，候选和独立复核都必须给出预计工时；超过 70 分钟即换方向，90 分钟仅是实际执行的保险上限。
- 0-1 实现模块最多 4 个、运行组件最多 2 个、辅助机制最多 2 项；复杂状态机制和自定义算法只能选择一个困难轴。
- 全栈算法题只允许轻量持久化和一条 Playwright 主流程冒烟，不再叠加版本谱系、跨请求状态机或完整浏览器回归套件。
- 自动补题从全部历史构造“算法＋业务对象＋交互结构”方向签名，在进入最终盲审前淘汰三项同时命中的候选；两条独立 0-1 路线并行竞速，第一条通过后停止另一条。

## 本地出题政策精简（2026-09-22，`generation-v39`，旧通用口径）

- 硬门槛只保留：题型正确、困难或地狱、禁题、实质查重、唯一可验收结果、范围有界，以及 A/B 同题面同环境首轮执行和完整证据链。
- 题面字数、功能/实现模块数、运行组件数、复杂机制数、算法数和预计用时都是范围信号，不能单独决定通过、拒绝或难度。60 分钟是软目标，60～90 分钟预警；明显无法在 90 分钟运行上限内闭环才按范围拒绝，时间不参与难度定级。
- 0-1 只要求一个可持续使用、可直接验收的完整用户闭环；一条足够深的工作流可以单独成题，不强制拆成两个功能模块。
- Feature 默认在同一产品中新增边界清晰、可独立验收的小型完整并列模块，不扩展、重构或替换已有核心功能、核心状态机和主数据流。模块可有自己的对象、轻量生命周期和主流程，只复用来源项目的技术栈、应用外壳、身份/权限、导航、设计风格与构建部署，并只保留一至两个必要接入点；这类同应用模块仍记为 Feature，不因对象或流程独立改判 0-1。纯前端、纯后端和全栈来源分别保持原项目边界，不强行补另一端。
- Feature 仍只允许一个用户目标、一个工程核心和一条主流程，不新增独立服务、第二套复杂状态机、跨模块事务或大规模迁移。难度来自一个不可删除、深而窄的真实机制，不能靠普通 CRUD、字段数量或集成清单凑难度。
- “小型完整并列模块”等政策术语只用于内部选题，题面必须从项目特有的用户、对象、冲突或可观察缺口自然切入。不得固定使用同一开头、句序和结尾，不得把技术栈、外壳、身份、导航、样式和部署写成复用清单，也不得照抄内部范围规则；本地校验会直接拒绝政策原文泄漏，独立复核会比较近期题面的表达骨架。
- Compose 运行方式、测试框架和生产构建不得集中为固定末句。运行要求放在对应服务或页面的运行边界旁，测试放在它验证的规则或状态旁，构建放在前端资源或发布边界旁；最后一句必须回到本题特有的用户结果、失败结果或可观察状态。本地校验会拒绝同时打包两类以上交付要求的末句，以及包含三项以上通用交付标记的清单式末句。
- Bug 允许 1～3 个相关、可由源码确认的问题；一个复杂故障链可以单独成题。问题数量、补丁行数和文件数不构成困难依据，前置盲审只有困难或地狱才可启动 A/B。
- 固定出题政策、历史错题经验和本次真实重试原因分字段传递。首次生成不会再把永久规则或历史资料描述成“上一批候选未通过”。
- 0-1 单路线总上限为 12 分钟：每轮只生成一批一个候选，生成阶段使用 `medium` 且最多 6 分钟，最终独立复核保持 `high` 并固定预留 5 分钟，其余时间用于本地校验与编排。独立复核失败后默认舍弃方向，不再定向改写或串行复核第二候选。
- Feature 概念阶段使用 `medium`，每次只返回两个不同方向且最多 5 分钟；后续仍按新意、范围、困难度与真实代码位置过滤。Bug 植入前要求逐项源码位置、顶层证据覆盖和至少一个可核验的跨函数、跨阶段、耦合约束或非局部验证驱动；明确只是常规局部修法的候选在植入前淘汰，最终难度仍只由冻结源码 `high` 盲审裁定。

## 自动 Bug 准入统一（2026-09-19）

- 自动 Bug 的候选准入、Pair 创建和 A/B 完成后复评均只接受困难或地狱；简单和中等必须如实记录并拒绝，不能靠提高标签放行。
- 真实性审核只核对源码证据、历史重复、题面泄漏和范围。每道题允许包含 1～3 个相关、可分别核验的问题；一个复杂故障链可以单独成题。每项都要有独立触发条件、可观察失败和代码依据，禁止拆分同一现象或拼接互不相关的小 Bug。真实性审核不得根据补丁长短、问题数量或已知正确基线提前评定难度。
- 冻结带缺陷源码后，隔离副本删除 Git 元数据，只向开发者视角盲审提供最终用户题面和冻结源码。该盲审是出题阶段唯一难度结论，按定位、最小正确修复和必要验证的完整负担判级；短补丁不能自动判简单。
- 60 分钟是目标范围，预计 60～90 分钟只记录预警，不自动拒绝；明显无法在实际 90 分钟运行上限内闭环时才因范围拒绝。时间不参与难度评分。
- 已确认缺陷若仅有题面缺字、触发条件遗漏、措辞问题或根因/修法泄漏，保留冻结源码与缺陷方向，仅定向改写题面。只有真实性、重复、因果关联、范围或盲审难度不合格时才放弃方向。
- 用户题面以 180～900 字为软目标，100～1200 字为安全范围，保持单段并可直接转发给开发者。开头须自然交代项目对象、用户流程和影响范围，可从具体对象、操作或异常切入，不固定使用“基于本项目”等套话；各问题只写触发条件、当前错误和业务影响，不写根因、解决方法、文件、函数、命令或测试框架；结尾落在最后一个问题的具体业务后果，不加请求修复、确保正常或测试类通用收尾。
- 本节对应 `difficulty_policy` v4 与 `generation-v20`，覆盖下方历史段落中“自动 Bug 中等可提交”“单一根因”“单 Bug”“固定题面开头”“60 分钟硬拒绝”或由真实性审核预判难度的旧表述。

## 难度审核（2026-09-17 更新）

- 生成 0-1、Feature、Bug 候选前，必须在内部保存初始能力、本轮必要增量、最小正确方案、常规方案是否足够、关键设计取舍和不变量反例及验证判据。常规停机等待、简单内存状态迁移、版本检查或请求去重不能仅凭术语判为困难；Feature/Bug 不继承原项目算法的难度。难度不足时换方向或来源，不增加无关需求凑难度。
- 题面独立预审会移除生成者的难度标签及自评，依据最终题面和初始代码重新分析。自动创建的 Pair 保存完整预审依据、规则版本和审核模型。
- A/B 归档完成后先自动进行实际难度复评。默认只读题面、共同初始快照和简要验收状态，按“困难＝多模块/系统约束、关键设计取舍及复杂状态、兼容性、权限、并发、性能或异常链路；地狱＝极高决策复杂度、深度项目理解或大量边界调试验证”判断人类执行难度。出题阶段的“最多一项复杂机制/自定义算法”只是范围预算，不是困难的必要条件。初评仅在初始状态不清、等级边界难定或材料矛盾时追加 A/B 产物、差异及轨迹的定向核查。难度以最小必要实现为准，不受耗时、失败次数、额外实现或 GSB 胜负影响。
- 详情页提供“实际难度复评”和“重新复评难度”，展示等级、简短理由与对应题面约束；边界题还保留初评。页面区分准备材料、等待模型名额、快速定级、可选边界核查和结论校验。每次等待模型名额最多 2 分钟；快速模型调用上限 4 分钟，只有边界题再进行一次上限 6 分钟的定向核查。超时或仍无法定级则明确失败待检查，不会无限排队。每次模型原始返回先写入本地 SQLite 再校验；失败时可展开查看未通过校验的原始依据，但它不作为有效难度结论。旧题没有完整复评时显示“难度待复评”，需在详情页手动触发；升级不会自动重跑全部历史题，也不会重跑 Claude 或修改其产物。
- 未复评、失败、低于困难或题面/初始 SHA/最新 A/B 产物/轨迹摘要/验收变化导致复评失效时，导出列表、Excel 与 SOLO-QA 提交载荷都会阻止提交。人工选择更高标签或确认 GSB 不能绕过门槛。自动选源与父题提交资格分开：单侧归档产物通过独立来源检查即可入选，不要求父题难度复评或 GSB 完成；新题仍独立审核困难/地狱。
- 原始出题标签与实际复评分别保存；导出采用复评等级。录屏和 GSB 编辑不改变题目的客观难度，不使复评失效。复评只更新本地审核记录，不修改已提交的远端记录。

## 自动补题规则修正（2026-09-18，控制台 20260918.4）

- 执行要求、错题本材料与已确认的规则 C 拒绝分开传递。首次生成不会被误告知已有拒绝；冻结 Bug 已确认重复时结束该方向，不能要求在同一冻结线索内换一个缺陷。
- Feature 的概念、生成和审核共用 `pairwise/generation_policy.py`：首次也可选择已有功能上的平滑扩展，允许复用对象和入口，但不能重做已验收的核心行为与结果。只计算真实必要增量，仍须独立达到困难/地狱且在范围预算内完成。
- Feature 题面目标 300–480 字，本地接受 300–600 字；句数、分号、句长及通用交付项位置只作写作建议。真正的验收歧义、历史重复、难度不足和超范围仍硬拦截。0-1 的产品深度提示与共用范围预算保持一致，不再同时要求“允许多个必要技术难点”和机制合计最多一项。
- 派发与备题共用持久化的题型失败计数。Feature 的内容质量失败连续两次后可暂缓该类型 10 分钟；概念卡等技术超时只进入短重试，不累计质量失败，也会兼容释放旧版本误记的 10 分钟超时暂停。Bug 质量拒绝直接换真实方向或来源，不暂停整个题型。成功备题清除该类型失败计数。容量不足及用户取消不累计，服务重启不清空仍有效的技术短重试。已有合格库存可在暂缓期间正常领用。来源级方向查重、配额和冷却保持独立。
- 旧版运行验证路径的原始/预置对照、参考修复与来源复核证据保存在 `.data/seed-verification/`，仅用于历史兼容。当前自动 Bug 直接预置并静态审核，不调用该运行路径；不能沿用旧反馈要求实际运行或测试通过。
- 本次更新生成规则版本，使尚未领用的旧版本候选失效；已创建 Pair 的题面、产物、实际难度复评与轨迹不重写。

## 使用

2026-09-19 Bug 题面修订已由 `generation-v37` 覆盖：当前允许 1～3 个相关真实问题，一个复杂故障链可以单独成题；补丁、冻结快照、真实性审核和代码证据必须逐项覆盖。问题数量本身不构成困难依据，多个可直接定位的局部小修仍判简单或中等，并在植入前尽早淘汰。最终题面保持单段和可直接转发，开头按项目具体对象、操作或异常自然变化，结尾落在最后一个问题的业务后果，只总结问题，不泄漏正确实现或解决方法。

### 单侧迭代基线（2026-09-18）

- Feature / Bug 任一侧首轮结束且已归档，原始 JSONL、摘要、单轮记录、环境指纹、40 位 artifact SHA、唯一父提交及 Git tree 均可核验，工作区与产物一致，固定验收命令至少一项且无缺项、全部通过，即可作为来源。不等待另一侧，不依赖父题难度或 GSB；父题自身 A/B、GSB、难度复评与提交流程保持不变。
- 选源按“父 Pair + 子任务类型”原子锁定并保存 `source_pair_id`、`source_attempt_id`、`source_side`、`source_artifact_sha` 和 tree。每个父 Pair 最多一道 Feature 和一道 Bug，两种类型允许选不同侧；删除子题也不会释放配额。已有历史只在精确尝试及唯一子题均可核实时回填，歧义不猜填，也不借另一侧绕过历史已用来源。
- Bug 来源优先选择较新的已完成、已验证产物；同一项目链的另一产物正在生成或运行子题，不阻止使用不同且尚未用于 Bug 子题的固定产物。较新产物不可用时允许选择较早的合格产物，并按实际来源提交号标识基线，不称其为“项目最新代码”。同一父 Pair 的重复创建、A/B 同起点、固定提交和题面实质查重继续执行。这是本地选源策略，不是官方额外门槛。
- 两侧都合格时，选源使用人工确认的 GSB；胜者必须在合格候选中。无 GSB 或 Same 按验收归档结束时间选最早一侧。已锁定后不因另一侧完成或 GSB 改判替换 SHA。
- 来源锁分为可重试、生成中、冷却中、已创建；两个生成路线共用同一来源。生成租约定期续期，服务重启后过期租约可重新领取同一来源，新令牌会拦截旧工作线程的迟到结果。创建子题与来源锁转为“已创建”在同一数据库事务内完成。
- 每条路线先克隆固定产物并建立本地临时 main，核对 tree，之后只读检查代码，在隔离目录复现问题。基线被改写、产生未跟踪或忽略的构建物时拒绝候选。只有题面审核通过才创建 Pair 并启动独立远端仓库；推送前再次核验 tree，新题 A/B 都从同一个新 main SHA 起步。
- 自动 Bug 入口采用 `existing_first_then_seed + static_first`。系统先在同一冻结来源快照上并行启动两条独立只读路线，每条寻找 2～3 个属于同一用户流程或紧密相关功能、具有具体代码证据的现有问题；任一路线的整组问题通过另一轮独立源码复核后，直接基于原快照生成题面，不修改基线。两条路线都未找到合格问题组，或找到的问题在完整题面、查重与困难度审核中未通过时，才进入埋 Bug 兜底。兜底一次模型调用最多返回两张简短设计卡，每张卡包含 1～3 个相关、可分别核验的问题；先从干净来源植入候选 A，失败时恢复原始 SHA 后再植入备用 B，源码中始终只存在一个候选问题组。API 显示总策略 `bug_generation_strategy=existing_first_then_seed`；最终任务按实际路径记录 `existing_first` 或 `existing_first_fallback_seed`，并保留静态证据与 `runtime_verified=false`。完成后的 A/B、难度复评和录屏流程不变。
- Bug 选源优先尚未尝试或更久未尝试的合格来源；来源冷却清零连续失败计数后，不会因此重新挤到未尝试来源前面。已有来源资格、有限冷却、历史方向记录和一来源一同类型子题的配额仍保留，Feature 的选源顺序不变。
- 概念卡先写最小正确方案；设计阶段的错误修法反例可留空，生成者难度自评分“足够／不足够／有争议”不能凭自评否决或放行。最终仍由独立审核严格判困难或地狱；若困难结论依赖“局部修法遗漏边界”，盲审必须给出可核验的具体输入、状态序列或操作交错。Feature 的 `high` 直接拦，`medium` 只有确认相同新增核心行为及验收结果才拦；Bug 的 `medium/high` 均须确认同一缺陷根因、触发链和失败结果，并提供历史题目标识及具体依据才提前拦截，否则携带相似警告进入完整题面独立复核，缺少独立结论不得批准。确认重复计入规则 C；容量、补丁格式和验证环境故障不作为质量失败，Bug 单来源使用双设计卡和 45 分钟绝对上限。
- 规则 C 记录按“来源 Pair + 子任务类型 + 方向指纹”保存，指纹结合代码位置、已核实机制与不变量，不根据题面措辞或笼统报错猜测。A/B 设计卡的失败方向分别保留并反馈到后续生成；Bug 仅将按当前具体故障链口径重新确认的方向作为硬排除，旧记录保留原身份和理由并以 historical_direction_warnings 提示重新核对，不能因旧理由写着已排除就直接放弃。确认结果另存版本化复核表，不覆盖历史记录；Feature 已确认重复的方向仍排除。精确相同的已确认方向直接拒绝，语义查重和独立审核继续执行。Bug 查重比较具体修复任务：原 0-1/Feature 的一般正确性要求是功能契约，不能仅因正确结果、算法或主流程相同便推断历史已修复同一缺陷。历史无论题型，只要已明确以同一故障根因、触发链和失败结果为修复目标，仍判重复。找缺陷、预置、概念、生成、查重和独立审核共用 `generation_policy.BUG_NOVELTY_GUIDANCE`；后续序号不再给 Feature 或 Bug 增加“三项全新”的特殊门槛。同时把最近 30 道 GSB 历史题放进语义查重，避免换项目名重复同一缺陷。25 分钟只记录软目标，45 分钟到达绝对上限才停止；两个候选均因质量失败时保存方向并立即按最近尝试顺序轮换来源，不进入质量冷却。
- 累计三个新的不同拒绝方向，或连续三次来源生成失败后，仅该来源的该类型冷却 30 分钟，保存原因及恢复时间；其他来源和类型仍可推进。冷却到期重试固定来源并换真实方向，旧方向记录不清空。没有可用来源时先补 0-1，不永久封禁根项目。

- 导出列表按最新一组 A/B 的结束时间倒序，取两侧中较晚的实际归档结束时间，在后端排序后分页，每页 20 条。修改 GSB、重新录屏、确认资料或同步提交状态都不会改变排序。缺失结束时间的历史记录显示“未记录”并排在末尾，不借用修改时间；结束时间相同则按创建时间、Pair ID 倒序稳定排列。
- 任务列表与导出列表采用自适应列宽：任务列表项目栏包含仓库、任务类型和难度；导出列表将难度单列展示，最右侧提供“删除”。删除经二次确认后从任务列表和导出列表隐藏，不删除数据库、轨迹、录屏、产物文件或远端提交；同时移除该题的勾选与展开状态，当前列表有未保存的 GSB 时会提醒。正在提交时不允许删除。结束时间用醒目卡片展示；长标题悬停可看全，资料问题和 SOLO-QA 完整反馈可在展开区查看。窄窗口自动改成卡片排列，不依赖横向滚动；题面、A/B Session、可编辑 GSB、录屏及勾选提交操作保留。

- 页面上方的“自动补题”以 0-1 / Feature 迭代 / Bug 修复长期约 1:1:1 为选题偏好；均衡模式下三个同时活跃的后台备题通道必须分属三种不同题型，某一题型短暂退避时为它保留空位，不再让第二个 0-1 抢占。每次按当前数量与可用来源选择可执行类型：优先补有合格基线的欠缺类型，没有可用来源时等待相应来源或短重试；新产物归档后再重新计算。可立即开始或预约 0–168 个整小时后开始，开启后持续补题直到手动关闭。题面使用独立的 Codex 后台额度同时竞速两条路线，第一条通过困难度、范围与去重复核后立即停止另一条；只有胜者创建 Pair、写入历史题库并启动 A/B。题面生成不占 Claude 并行名额；有 Claude 空位时先领用已审核的待选题面，否则直接出题并启动 A/B。独立的后台备题线程不等待 Claude 满载：自动补题开启且库存低于 4 道时，就与创建/派发流程同时生成已审核题面；Claude 满载时创建流程也可继续预生成，数据库入库上限仍为 4 道。后台备题按题型缺口和待选库存选来源，来源租约避免与派发流程争用同一基线。每个 Feature/Bug 来源只备一道，0-1 可备多道不同题面；不提前创建仓库，领用时再次核对规则版本、历史重复和来源快照。三类都必须通过困难或地狱复核。0-1 从空 README 建立新项目；Feature 迭代扩展归档产物；Bug 修复从未被同类型重复使用的归档产物建立新 Pair。停止补题会终止在途竞速路线但不影响已启动的 A/B。
- Pair-wise 已创建题目仍只追加到项目根目录的 `gsb历史题库.md`，不把旧版题目算作新的 Pair。独立的“待选题面库”保存已通过审核但尚未创建 Pair 的自动候选：Claude A/B 名额满后即使没有排队任务，也继续补足最多 4 道待选题面；空位出现后优先领用。候选之间也会排除相同及高度相似的题面，并作为后续生成的历史上下文；候选在创建前重新核对历史、难度规则版本、固定来源 SHA/tree 和原有来源锁；崩溃后已创建的 Pair 会回填为“已使用”，过期锁可恢复，人工可带原因驳回未领用候选。状态及题面保存在 SQLite，不改变 A/B 的原始题面与轨迹。
- 待选库的“更新 zzzz 旧题库”只读扫描 `zzzz` 顶层项目中的首轮用户题面，并结合旧版 `history-prompts.md` 建索引。对于旧运行记录中题面完整、类别明确且有固定容器验收命令的困难/地狱级 0-1 题，另建可复用目录。自动补题先按类别领用一题，独立复核难度、范围和与当前 `zzzz-gsb` 已用题的语义重合；通过后才进入待选候选并创建新 Pair。手动建题与自动领用都在创建事务中再次排重；确定性排重仅以现有 GSB Pair 和 `gsb历史题库.md` 为边界，`zzzz` 本身不再是排除来源。只复用题面，不复制旧代码、依赖或轨迹。旧 Feature/Bug 依赖已有代码基线，暂不作为空仓库题直接复用；可在页面查看每道旧题状态并将待复核题置顶。首次使用需在待选库页面点击更新，之后可按需重建，不改动 `zzzz`。
- 当前自动 Feature/Bug 的代码基线只从已归档 Pair 选择。`zzzz` 旧项目代码基线入口目前未接入自动调度，不能作为备题兜底；保留的 legacy 模块与字段用于历史兼容。`zzzz` 旧 0-1 题面复用仍可用，它不带入旧代码，与代码基线选源是两条不同流程。

- 初次点击会在同一事务中同时建立 A/B 两条执行记录，再交给两个并行工作线程；运行并行上限必须至少为 2。每侧可保留多个失败的独立 Session，最后一次为交付候选；成功结果不能因质量或偏好再次执行。
- 网络/API 错误后不输入“继续”“重试”或任何文字。保存现场后为同一侧创建新的独立 Session，旧尝试仍可查看。
- 如果 A/B 都在发送 Prompt 之前因环境工程问题失败，先分别点击两侧的“停止并保留现场”，等旧容器清理标记完成，再点击“同时重建 A / B 独立 Session”。新的两条 Session 在同一事务中建立，复用原 main 快照和冻结配置；旧失败记录保留。任一侧已发送 Prompt 时不允许走这条双侧重建路径。
- Git、轨迹或验收归档异常使用“重新归档（不调用模型）”，该操作不会向 Session 输入内容。
- 服务重启只恢复排队、监控或归档。启动步骤不确定时保留现场并报错，不猜测是否已经发送 Prompt。“检查并恢复归档”属于占用并行名额的收尾任务，重启后继续检查，不发送题面。旧版本仅因 90 分钟超时而失败、仍遗留容器的最新尝试会自动进入一次收尾检查；已经手动停止、已被重试替代或已完成的记录不会被恢复，收尾失败也不会无限自动重试。
- 手动启动录屏时只接受一个立即执行的 Pair 批次，不建立跨题等待队列：已有录屏批次或服务正在安全更新时，本次请求直接报错且不写入等待状态，当前录屏结束后需重新点击。一次选择 A、B 时，两侧属于同一批次并连续依次录制，避免争抢前台窗口。已接受批次使用数据库状态恢复，服务正常停止时中断的本批录屏会在重启后继续；从未点击“开始录屏”的已完成 Pair 不会被自动加入。技术失败会保留已生成的视频和错误并继续本批下一侧。首次使用须在 macOS“隐私与安全性 → 屏幕与系统音频录制”中允许运行控制台的 Codex/终端，授权后重新开始录屏即可。
- Feature / Bug 未通过规则 C 时，只保存该来源的方向证据，按上述单侧基线规则换方向、换来源或暂时冷却，必要时先补 0-1。不会通过改标签或换措辞放行雷同题。Bug 概念卡围绕冻结预置快照中的具体故障，不要求发明新模块；规则 C、静态代码证据和困难度独立复核仍保留。
- 生成中展示当前来源、两条路线的真实阶段、本阶段耗时、本题累计耗时、Bug 单来源预算、规则 C 定向改写次数及保留的上次未通过原因，不提供虚构百分比。并行名额满时显示“等待名额”；Feature/Bug 失败按来源冷却，连续新 0-1 生成失败 3 次后暂停并显示“需要处理”，已有 A/B 继续运行。调度每 3 秒检查，不立即自唤醒空转；“开启”不等于“正在生成”。
- 最近三次出题失败按题型和根项目保存，重试时把匹配的拒绝原因送回生成器；0-1 的批内重试也保留原有出题要求和历史反馈。难度不足或重复须换核心方向，不靠堆需求、改标签或清空规则 C 记录放行。暂停面板实时检查当前基线，显示恢复后优先尝试的题型和来源；旧调度原因收进展开记录，不再冒充当前阻塞。点击“继续自动补题”才恢复，刷新页面或服务重启不会自行开启。
- “本地补题错题本”持久保存候选题面或概念卡、失败环节、原始审核意见、来源快照及规则版本。自动补题和手动生成草稿均接入；A/B 完成后被复评为简单或中等的题也会收录。相同候选及问题重复出现时累计次数，每次依据仍单独保存；网络、模型等生成故障会标为“生成故障”，不参与选题经验检索。
- 每次出题最多检索 3 条相关、待处理的本地记录，优先相同来源，再考虑题型、项目类别及算法/流程文本匹配。资料仅供重新核对，不写入规则 C 排除名单，也不直接决定新题难度。页面支持搜索、类型/处理状态筛选及带依据的“已处理”“判定有误”标记；这两种状态退出检索，原文与处理历史保留。后续候选通过、创建新 Pair、完成实际复评均可追加关联结果，不自动宣称原问题已解决。
- 完整内容同步到项目根目录 `gsb本地补题错题本.md`，可从页面下载；该文件是自动维护的阅读副本，处理意见请在页面保存。远端质检同步后，仅将明确涉及难度、雷同或题面歧义的负面意见回流为出题经验，按远端编号、状态和原因去重；录屏、附件或提交操作问题不写入出题错题本，也不自动禁用整个来源。`gsb错题本.md` 继续保留其他远端质检经验。
- 自动题面生成期间，任务列表最上方会出现“正在生成”记录，展示真实阶段、累计耗时和生成开始时间，A/B 显示“等待题面”，编号与难度分别显示“待编号”“待复核”。这条记录参与后端搜索和每页 20 条分页，但不提前创建正式 Pair、不占题型配额或进入导出列表。通过复核后沿用预留 ID，自动替换为正式任务并启动 A/B，不出现两条重复记录；取消或生成失败时不保留虚假的正式任务，原因仍在自动补题区域查看。
- Bug 来源在设计前检查冻结 Git 快照；含未展开子模块或越界符号链接时直接记录为不兼容，不进入设计、植入、题面或难度调用。候选 A、B 分别从同一冻结 SHA 创建独立临时 Git 副本，候选失败不通过 checkout 恢复后复用工作区。同一来源在同一生成规则版本下两轮均因难度不足失败后停止筛查；超时、容量或环境故障不计入这两轮。
- “停止并保留现场”仅停止对应容器。缺少轨迹且题面已经发送时保留停止后的容器，避免丢失证据。
- 题面发送记录不等于 Claude 已接受首轮。系统只读检查当前题面对应的原始 JSONL；发送后 5 分钟仍未发现时，停止该侧容器并再次核查。若轨迹在停止前出现，沿用原会话的正常归档或失败收尾；若仍没有匹配轨迹，保留已停止容器、工作区和终端日志，标记“首轮启动未确认”供人工检查，不在原 Session 再按回车、补发题面或自动新建 Session。
- 达到 90 分钟时，若最近 10 分钟仍有轨迹活动且轨迹或终端表明正在进行最终测试、构建、回归或验收收尾，则自动延时 15 分钟并继续只读监控；否则立即进入“检查并恢复归档”。105 分钟为无条件硬上限。进入收尾后会停止原容器、冻结工作区并保存完整原始 JSONL，再核对完成边界。若原首轮已完成且题面、SessionID、Harness 与单轮约束均通过校验，只补归档、产物快照和原有验收；验收失败照实保留，不修代码也不重新调用模型。未完成或不合规时标为“需要处理”，保留停止后的容器、工作区和原始证据；停止/复制失败显示具体错误，不假报清理成功。耗时不进入 GSB 评价。
- Claude 返回 `408/429/500/502/503/504` API 工程错误时，系统立即保存该次原始轨迹并关闭旧 Session，不发送“继续”“重试”或其他追加内容；随后只为失败侧从共同 main 初始 SHA、相同完整题面和冻结配置创建新的独立 Session。每侧最多自动重跑 2 次（最多 3 次尝试），失败尝试保留为工程故障审计记录但不作为有效 A/B，也不参与 GSB 或难度判断；次数用完后停止该侧并等待人工处理，不换题、不重跑另一侧。
- 其他失败且已发送题面的最新尝试，在详情页提供“检查并恢复归档（不重跑）”。这是停止并检查原现场的操作，不是追加“继续”或新建 Session；B 不会因恢复 A 而重跑。收尾后仍缺少完成边界的题目保留失败记录，由用户决定后续处理。
- 每个 Pair 创建一个独立仓库。远端分支集合从创建到交付始终精确为 `main`、大写 `A`、大写 `B`。main 固定为共同初始快照，产物提交分别使用最终 Git tree 和 main 作为唯一父提交；A/B 只前移到本侧产物。新建本地项目根目录统一使用“列表编号-仓库名”：根题如 `0008-project-name`，衍生题如 `0001-4-project-name`，不再使用独立的数据库流水号作文件夹前缀；内部固定以 `main`、`A`、`B` 区分共同起点和两侧工作区。已有执行记录的旧 Pair 保持原目录，重试也继续沿用原路径，不修改轨迹或录屏地址。
- 人工评价带版本检查，避免多标签页相互覆盖。更新证据后需重新确认人工评价。未提交的评价可恢复本机草稿。

## 本版范围

- 自动执行 Harness 为当前项目已有的 Claude Code Docker 镜像；不提供原生 Codex Session 启动和轨迹解析。
- 手动点击开始后的录屏流程只负责演示真实产物，不替代专家判断。只有专家打开 A/B 本地视频核对并分别勾选确认后，录屏字段才算交付完整；对象存储上传由 SOLO-QA 提交接口在选择本地视频后完成。
- 录屏由已授权的 Python.app 加载本机原生捕获组件；首次使用通过系统 clang 编译并缓存，不安装额外依赖。演示结束并展示最后结果后立即停止捕获、保存视频，不再等待 88 秒后裁剪；失败时也正常结束捕获并保留已录到的过程。终端与页面录制均保留鼠标，终端统一使用上述字号、窗口和正文裁切设置。重录前原视频移入本项目 `录屏/历史录屏/<时间戳>/`，以便新录制失败时找回。
- 页面填写已有内容的控件时执行原生“全选→删除”，确认已清空后才输入。多行内容、达到 40 字符的长段文字和命令、JSON、路径等整段粘贴，普通短文字保留快慢变化的输入节奏；输入不一致时报告具体控件和字符数，操作日志记录失败动作，不把录屏脚本故障误报为产物验收失败。
- 页面录屏开始前先通过只读命中检查，选择页内非控件、非文字的空白位置放置鼠标；密集页面无合适空白时在页内左侧边缘起步，不点击、不滚动、不改变焦点。录屏助手对保留鼠标的页面模式不再执行终端的右上角避让。输入完成后不自动按 Tab、不提前跳到下一控件；先移动鼠标到下一个目标、短暂停顿，再真实点击获得焦点。终端录屏同样保留鼠标，指针停在正文区域内；已有视频不会被自动重录。
- 每次终端录屏都新建带唯一标识的专用 Terminal 窗口，不在用户原有窗口或标签页执行命令；结束时仅在窗口 ID 与专用标题同时匹配时关闭该新窗口。终端窗口定位失败或编码失败时报告录屏失败，并保留已生成的片段；所有终端任务（含无类别的通用工程）都禁止退回整屏录制。每次捕获前将专用窗口置于前台，并读取实际边界，只捕获其正文区域；捕获期间须保持窗口位置、大小和前台状态。原生区域捕获复用 Python.app 已有录屏权限。
- 详情页的录屏指南优先使用冻结项目类别，结合冻结题面、语言/框架和固定验收命令生成。页面演示路线会只读参考各自产物，定位实际控件，不修改产物代码。后端任务录制终端的启动、测试和 verify 输出；纯前端及全栈正常启动时录制页面交互，后台启动日志保存在录屏状态目录中。如果原始 Compose 页面容器确认崩溃，则从干净容器状态重演启动并仅录制终端中的真实状态和报错，完成后显著标为“原始产物启动失败过程”，仍须人工核对，不修改 A/B 产物。
- Pair-wise 提交复用仓库内的 Chrome 提交助手，但使用独立的 GSB 接口、双轨迹、双录屏字段和本地提交状态表，不把旧单轮五维字段套进新表单。扩展须在 Chrome 扩展管理页重新加载到 v1.4.4 或以上；该版本支持 A/B 交付完整性评分和描述，会按真实 `.jsonl` 文件名上传轨迹，并按照 SOLO-QA 的字段协议将轨迹作为附件数组、录屏作为对象存储 URL 提交；单个文件上传遇到瞬时网络中断时会自动重试一次，并标明具体失败阶段。
- 旧多轮自动补题、五维评分、21 分门槛、自动修复和多轮续问在默认模式下不启动。新自动补题负责三类题面的均衡选择、确定性校验、产物快照选源、Pair 创建与 A/B 同时启动；两侧归档后由人工核对证据并填写 GSB。
- `CLAUDE_EVAL_LEGACY_MODE=1` 仅用于明确需要运行旧版的历史兼容环境；切勿用旧版流程采集本期数据。
